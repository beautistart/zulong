# 任务执行过程 ↔ 记忆图谱 ↔ 经验库 三猜想分析

> 分析日期：2026-05-27
> 依据文档：TSD v1.7（§9.3-9.7 三库分立、§11 经验库增强、§18 记忆系统深度增强、§19 图记忆全生命周期、§23 前端交互体系）
> 关联文档：[任务执行记忆化与经验化架构任务书](../任务执行记忆化与经验化架构任务书.md)

---

## 猜想 1：能否将任务执行过程（工具调用、审批等）加入记忆/记忆图谱？

**结论：能，且 TSD v2.7 已设计，部分已落地，但有缺口。**

### 1.1 已落地的部分

根据 TSD §19.2.1 和 `memory_graph.py` 第 50-62 行，MemoryGraph 已有 **11 种节点类型** 和 **7 种边类型**，其中与任务执行直接相关的有：

| 节点类型 | 来源 | 已落地 |
|----------|------|--------|
| `TASK` | TaskGraph.TaskNode | TaskGraphAdapter 投射 |
| `DIALOGUE` | 对话轮次/子对话 | DialogueAdapter 投射 |
| `EPISODE` | 情景摘要 | `_persist_event_to_memory()` 写入 |
| `FILE` | 任务文件引用 | TaskGraphAdapter 投射 |
| `EXPERIENCE` | 经验文档 | ExperienceAdapter 投射 |

在 `ide_fc_runner.py` 中，已有 **5 个钩子** 将任务执行数据注入 MemoryGraph：

| 钩子 | 行号 | 注入内容 |
|------|------|----------|
| `_persist_event_to_memory()` | ~1790 | 执行阶段事件 → `EPISODE` 节点（含 `approval_required`、`tool_requested` 等 10 种阶段） |
| `_record_sub_dialogue()` | ~1887 | 单次工具执行 → 子对话 `DIALOGUE` 节点 |
| `_finalize_dialogue_round()` | ~1905 | 轮次总结 → FAISS 侧车索引 |
| `_auto_save_session_memory()` | ~4919 | 全对话摘要 → `KNOWLEDGE` 节点 + 触发 `ExperienceGenerator` |
| `_emit_memory_diff_async()` | ~1551 | 工具执行后 → `graph:memory:diff` WS 消息 |

TSD §23.6 明确描述了：

> **C. 任务总结记忆变化**：任务完成后，哪些记忆新增/强化/淘汰了 — MemoryGraph.get_diff()

### 1.2 缺口（尚未落地的部分）

1. **工具调用缺少独立节点类型**：当前工具调用仅作为 `DIALOGUE` 的子对话节点存在，无独立 `TOOL_CALL` 节点。这意味着：
   - BFS 扩散无法将工具调用作为独立实体进行关联
   - 无法跨任务对同一工具的使用模式进行图遍历
   - 赫布学习无法在工具调用之间形成共激活关联

2. **审批决策未持久化为图节点**：审批 (`approval_required`) 仅在 EPISODE 节点的 `phase` 字段以字符串存在，无独立的 `APPROVAL` 节点，无与 TASK/FILE 的结构化边。

3. **缺少 `TOOL_RESULT` 作为对等节点**：工具输入和输出未形成 CAUSAL 边对 (`TOOL_CALL → TOOL_RESULT`)，导致无法追踪"哪个工具造成了什么效果"。

4. **工具链序列未形成 TEMPORAL 链**：同一任务内的工具调用序列无 TEMPORAL 边连接，无法表达执行顺序的因果。

### 1.3 可行性验证

MemoryGraph 的架构完全支持新增节点/边类型。添加新的 `TOOL_CALL`、`APPROVAL`、`TOOL_RESULT` 节点和 `TOOL_RESULT → FILE` 的 REFERENCE 边，与现有的 11 节点 + 7 边的模型完全兼容。

## 猜想 2：如果可以进入记忆，以何种方式从什么点切入记忆？

**结论：三条切入路径，优先级依次递减。**

### 2.1 路径 A（推荐）：FC 循环执行边界 → EPISODE 节点扩展

**切入位置**：`ide_fc_runner.py` 中的 FC 循环 4 个工厂方法边界

```
Check → Call Model → Exec Tools → Eval Response → [循环]
                      ↑                      ↑
                   切入 1                  切入 2
```

- **切入 1（`_exec_tools()` 之后，行 3537）**：每轮工具执行完毕，已有 `_emit_memory_diff_async()` 在此触发。扩展该钩子，将单轮的工具调用信息（工具名、参数摘要、成功/失败、耗时）打包为一个 `TOOL_CALL` 图节点。
- **切入 2（`_eval_response()` 之后）**：每轮 FC 结束，创建本轮 `TOOL_CALL` 节点之间的 TEMPORAL 边链。

**方式**：新增 `TOOL_CALL` 节点类型 + 在 `_persist_event_to_memory()` 中为 `tool_requested` / `tool_finished` 阶段创建独立图节点（非仅 EPISODE 节点）。

**图结构示例**：

```
TASK (o1_1)
  ├── HIERARCHY → TOOL_CALL (tc:search_codebase_1)  [importance=NORMAL]
  │    ├── REFERENCE → FILE (affected file)
  │    └── CAUSAL  → TOOL_RESULT (tr:search_codebase_1)  [success=True, latency=230ms]
  ├── HIERARCHY → TOOL_CALL (tc:read_file_2)  [tool_name=read_file]
  │    └── CAUSAL  → TOOL_RESULT (tr:read_file_2)
  └── HIERARCHY → APPROVAL (ap:execute_command_3)
       ├── CAUSAL  → TOOL_CALL (tc:execute_command_3)  [was approved]
       └── metadata: {mode: "whitelist", risk: "HIGH", whitelist_entry: "npm run build"}
```

### 2.2 路径 B：审批流边界 → APPROVAL 节点独立化

**切入位置**：`ide_fc_runner.py` 行 1106-1135 审批流 + WebSocket `approval:required` 消息后

TSD §23.4 定义了完整的 4 模式审批流（`full_auto` / `whitelist` / `manual` / `popup`），当前仅在 EPISODE 中以 `phase="approval_required"` 存储。应独立化为 `APPROVAL` 图节点。

审批节点元数据设计：

```python
{
    "tool_name": "execute_command",
    "risk_level": "HIGH",
    "approval_mode": "whitelist",
    "decision": "approved",         # approved / denied / whitelisted
    "reason": "用户批准了 npm run build",
    "added_to_whitelist": True,
    "latency_ms": 1200,
}
```

审批节点通过 CAUSAL 边指向被批准/拒绝的工具调用节点，形成可追溯的审批-执行因果链。

### 2.3 路径 C：任务完结边界 → ExperienceGenerator 触发

**切入位置**：`ide_fc_runner.py` 行 4919 `_auto_save_session_memory()` + 行 4991 `ExperienceGenerator.process_dialogue_batch()`

当前已触发经验提取，但提取粒度不足——输入的是原始对话文本，不是结构化的工具链。改进：将整个任务的 TOOL_CALL 序列 + APPROVAL 序列打包为结构化摘要，送入 `ExperienceGenerator` 或 `ExperienceExtractor.extract_from_buffer()`。

### 2.4 三种切入路径对比

| 维度 | 路径 A (FC边界) | 路径 B (审批边界) | 路径 C (任务边界) |
|------|:---:|:---:|:---:|
| **实时性** | 每轮 FC 结束 | 每次审批决定 | 每个任务结束 |
| **数据粒度** | 工具级 | 审批级 | 任务级 |
| **BFS可达性** | 高（与TASK直连） | 高（与TOOL_CALL直连） | 低（仅KNOWLEDGE节点） |
| **实现复杂度** | 中（需新增节点类型） | 低（新增节点类型+钩子） | 低（已有钩子，需增强） |
| **经验化潜力** | 最高（细粒度模式） | 中（用户偏好模式） | 中（任务级总结） |

**建议采用路径 A + B 组合**，路径 C 在此基础上自动受益。

## 猜想 3：如何将任务执行经验化/提取经验？

**结论：四级经验分层 + L2 结构化提取管道。**

当前系统已有两套经验提取器：

| 提取器 | 方式 | 输入 | 输出 |
|--------|------|------|------|
| `ExperienceGenerator` | 规则模式匹配 | 对话文本 | 成功/失败/偏好经验 |
| `ExperienceExtractor` | L2 LLM 提取 | 对话 buffer | 结构化 JSON 经验 |

但两者都**以对话文本为输入**，缺乏对工具链结构的感知。改进如下：

### 3.1 四级经验分层模型

```
Level 1 — 工具级经验 (单次工具调用)     → 即时效用
  ├─ 成功模式: tool返回期望结果 + 耗时 < 阈值
  ├─ 失败模式: tool返回异常/空结果/超时
  └─ 用户反馈: tool后用户立即评论 (+/-)
       ↓ 聚合
Level 2 — 链级经验 (工具序列)           → 执行策略
  ├─ 高价值链: 工具序列 A→B→C 导致任务快速完成
  ├─ 反模式链: 同一工具被调用 ≥5 次 → 警示
  └─ 合作链: search → read → edit → execute 四步闭环
       ↓ 聚合
Level 3 — 任务级经验 (单次完整任务)     → 避坑指南
  ├─ 成功路径: 任务整体成功，提取关键决策链
  ├─ 失败路径: 哪一步后任务开始偏离，诊断"分水岭"
  └─ 审批模式: 哪些工具总被批准/拒绝 → 用户偏好
       ↓ 聚合（跨任务）
Level 4 — 跨任务经验 (模式挖掘)         → 元知识
  ├─ 高频模式: 哪些工具序列在多个任务中出现
  ├─ 进化模式: 白名单如何随时间演化
  └─ 领域经验: network领域的修复通常需要哪些工具
```

### 3.2 流水线设计

```
TOOL_CALL 节点序列
  │
  ├──[Level 1] 规则引擎
  │   每轮 FC 结束 → 检查 tool_result
  │   - 成功+快速 → EXPERIENCE 节点 (+1 成功权重)
  │   - 失败/超时 → 标记 LOW 强度，供衰减修剪
  │   - 用户即时反馈 → HebLearning 加强关联
  │
  ├──[Level 2] 序列模式检测 (每任务结束)
  │   - 滑动窗口检测 N-gram 工具模式
  │   - 与现有成功链匹配 → 经验强化
  │   - 检测到反模式 → 创建 WARNING 型 EXPERIENCE
  │
  ├──[Level 3] L2 结构化提取 (每任务结束)
  │   - 输入: {tool_chain: [...], approval_log: [...],
  │            success: bool, circuit_breaker_events: [...]}
  │   - 调用 ExperienceExtractor.extract_from_buffer()
  │   - 输出: {lesson: "...", pattern: "...",
  │            do_again: [...], avoid: [...], confidence: 0.X}
  │   - 入库: EXPERIENCE 节点 → 经验库 RAG
  │
  └──[Level 4] 离线模式挖掘 (定期)
      - 扫描所有 EXPERIENCE 节点
      - 对同一领域的多个经验做聚类
      - 提升高频模式的 importance → IMPORTANT/MUST_REMEMBER
      - 淘汰已不再相关的冷经验
```

### 3.3 与现有记忆系统的整合

**入库**：四级产生的 EXPERIENCE 节点通过 `ExperienceAdapter.sync()` 投射入 MemoryGraph，`add_experience()` 写入 `ExperienceStore`（向量 + BM25 混合检索，TSD §11.1）。

**检索**：`retrieve_context()` 双路并行检索时，EXPERIENCE 节点已特殊处理——通过 `resolve_backend_ref()` 解析 `exp:{doc_id}` 获取完整经验文本（`memory_graph.py` 行 2672-2676）。

**FC 注入**：当 L1-B 通过 `ExperienceStore.search()` 命中相关经验时，在 `retrieve_and_inject()` （TSD §9.4.1）阶段拼入 L2 prompt，形成经验闭环。

**生命周期**：已提取的经验走完整的九阶段生命周期（TSD §19.10），通过赫布学习（共激活增强）、艾宾浩斯衰减（不提则忘）、LLM 审查（重要度晋升/淘汰）自然演化。

## 总结

| 猜想 | 结论 | 关键依据 |
|------|------|----------|
| 1. 能否加入 | **能，已部分落地** | TSD §19.6.2 TaskGraphAdapter 已投射 TASK 节点；`_persist_event_to_memory()` 已写 EPISODE 节点；缺口是缺少 TOOL_CALL/APPROVAL 独立节点类型 |
| 2. 如何切入 | **三路径：FC边界(A)、审批边界(B)、任务边界(C)** | A 路径在 `_exec_tools()` 后（行3537）注入 TOOL_CALL 节点；B 路径在审批流返回后注入 APPROVAL 节点；推荐 A+B 组合 |
| 3. 如何经验化 | **四级分层提取：工具级→链级→任务级→跨任务级** | 已有 `ExperienceGenerator` (规则) + `ExperienceExtractor` (L2)；在此基础上增强结构化工具链输入，四条 LLM 审查路径可自然嵌入 |

**整体判断**：该猜想完全可行，与 TSD 架构对齐，新增工作主要是补齐 3 个节点类型 + 增强经验提取器的结构化输入能力。
