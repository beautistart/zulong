## 1. 背景与动机

### 1.1 需求来源

用户反馈希望祖龙提供一个桌面端程序，而非仅通过浏览器访问。核心诉求包括：

- 独立的应用窗口，不被淹没在浏览器标签页中
- 系统级集成（托盘常驻、原生通知、全局快捷键）
- "双击图标就能用"的体验

### 1.2 评估目标

本文档旨在从技术架构、工程成本、用户体验三个维度评估桌面端的可行性和方案选型，避免盲目开发或重复造轮子。

## 2. 祖龙部署场景分析

祖龙有三种核心部署场景，桌面端需求仅覆盖其中一种：

| 场景 | 所需模块 | 界面形式 | 是否需要桌面端 |
|------|---------|---------|-------------|
| 🤖 **机器人端侧部署** | core + full（摄像头/麦克风/L1全套） | Web 远程监控后台 | ❌ 不需要 |
| 🖥️ **服务器端部署** | core（推理/记忆/工具） | Web 端 | ❌ 不需要 |
| 💻 **单机用户** | core + Web UI + VS Code 桥 | 希望是桌面应用 | ✅ 需要 |

**关键原则**：三种场景互不干扰，各取所需。桌面端只是为单机用户增加一种可选的启动方式，不改变现有任何架构。

### 2.1 当前架构的模块化支持

祖龙的 `ModuleManager`（[module_manager.py](../../zulong/launcher/module_manager.py)）已经通过 `mode_tags` 体系支持按场景组装模块：

```
mode_tags 体系:
  {"core"}     → 任何模式都启动（Config、MemoryGraph、InferenceEngine...）
  {"full"}     → 仅 Full 模式启动（摄像头、麦克风、L1-A反射、技能包...）
  {"optional"} → 可运行时动态开关

启动模式:
  IDE 模式 → core + Web UI + IDE 后台桥 → 单机用户 / 服务器部署
  Full 模式 → core + full + Web UI + IDE 后台桥 → 机器人端侧
```

> 详细架构说明参见 [祖龙模块化技术架构](../../AGENTS.md)。

## 3. WebSocket 通信分析

### 3.1 当前通信架构

```
┌──────────────────┐     WebSocket      ┌──────────────────┐
│  前端 (Web/IDE)  │ ◄────────────────► │  Python 后端     │
│                  │  ws://127.0.0.1:   │  (FastAPI)       │
│  - Web 聊天界面   │   8090/ws (Web端)  │                  │
│  - VS Code 插件  │   8090/ide (IDE端) │  - L1-B 调度     │
│  - 记忆图谱      │                    │  - L2 推理       │
│  - 审批面板      │  心跳: 30s         │  - MemoryGraph   │
│                  │  超时: 5s          │  - TaskGraph     │
│                  │  断连: 3次丢失     │  - FC 循环       │
└──────────────────┘                    └──────────────────┘
```

### 3.2 本地 WebSocket 的性能特征

| 通信方式 | 典型延迟 | 适用场景 |
|----------|---------|----------|
| 进程内函数调用 | ~纳秒 | 单体桌面应用 |
| 共享内存 (SharedMemory) | ~微秒 | 高频传感器数据（祖龙已有） |
| 本地 WebSocket (127.0.0.1) | ~0.1-1ms | 祖龙当前方案 |
| 远程 WebSocket | ~10-100ms+ | 云端通信 |

**结论**：本地 WebSocket 走 TCP loopback，操作系统内核对其有优化，延迟在 0.1-0.5ms。对于 LLM 推理（秒级），此开销可忽略不计。

### 3.3 潜在的瓶颈及应对

| 瓶颈 | 影响场景 | 现状 | 未来增强方向 |
|------|---------|------|------------|
| JSON 序列化开销 | 30fps 实时渲染 | 大消息分片（TSD v2.9.5） | 二进制帧 + protobuf |
| 单连接串行化 | 音频流 + 文本流并发 | Web（`/ws`）与 IDE（`/ide`）分属两个**历史遗留端点**，并非为并发专门设计的多路复用 | 真正的多路复用 |
| 高频帧数据传输 | 桌面宠物动画 | 渲染本地化 + WebSocket 只发指令 | 指令通道模式 |
| 断线重连 | 网络不稳定 | ⚠️ **当前无服务端消息缓存**（PendingMessageCache 尚未实现） | 待实现：消息缓存 + 自动重连 |

> ⚠️ **修订说明（v1.1）**：原稿将"双通道分离"和"PendingMessageCache 缓存 5 分钟"列为已落地方案，经代码核查均不成立——`/ws` 为历史遗留端点（`ide_server.py:2526` 注释称其为"旧端点"），`PendingMessageCache` 在代码库中无任何实现。桌面壳若要保证"后端崩溃/重启后前端无缝恢复"，需将服务端消息缓存列入后续任务，而非当作既有能力。

> 📌 **本节定位**：本节旨在确认"现有 WebSocket 架构不会成为桌面壳的瓶颈"，是**确认性结论**，并非桌面端诉求的论证依据（桌面端的诉求是窗口/托盘/快捷键，见 §1.1）。

**核心设计原则**：高频渲染（动画帧、物理模拟）→ 纯本地处理；AI 决策（情绪、行为、对话）→ WebSocket 发指令；用户交互 → WebSocket 上报。这与祖龙 L0 设备层本地处理 + L1-L3 事件驱动的架构哲学完全一致。

## 4. 技术方案对比

### 4.1 方案总览

| 方案 | 工程量 | 三端适配 | 包体积 | 用户体验 | 推荐度 |
|------|--------|---------|--------|---------|--------|
| **A. Electron 壳** | ⭐⭐ 低 | 天然跨平台 | ~150MB | 接近原生 | ⭐⭐⭐⭐⭐ |
| B. PWA | ⭐ 极低 | 浏览器层 | 0 | 有限 | ⭐⭐⭐ |
| C. 原生桌面 | ⭐⭐⭐⭐⭐ 极高 | 三端各写 | ~30MB | 完美 | ⭐ (不推荐) |

### 4.2 方案 A：Electron 壳（推荐）

#### 架构

```
┌─────────────────────────────────────────────────────────┐
│              Zulong Desktop (Electron 壳)                 │
│                                                          │
│  ┌──────────────────────────────────────────────────┐   │
│  │  BrowserView / webview                           │   │
│  │  → 加载 http://127.0.0.1:8090                    │   │
│  │  → 复用 100% 现有 Web 前端 (index.html 15600行)   │   │
│  └──────────────────────────────────────────────────┘   │
│                                                          │
│  壳层能力 (新增，不改现有代码):                            │
│  ├── 进程管理: spawn("python start.py")                  │
│  ├── 系统托盘: Tray + 右键菜单 (显示/隐藏/退出)            │
│  ├── 原生通知: Notification API                          │
│  ├── 全局快捷键: globalShortcut.register("Ctrl+Shift+Z") │
│  ├── 开机自启: auto-launch                               │
│  ├── 单实例锁: app.requestSingleInstanceLock()           │
│  └── 窗口管理: 记住位置/大小、最小化到托盘                │
└─────────────────────────────────────────────────────────┘
```

#### 与现有架构的关系（完全解耦）

```
                    ┌──────────────┐
                    │  Desktop 壳  │  ← 新增 (可选用)
                    │  (Electron)  │
                    └──────┬───────┘
                           │ HTTP (localhost:8090)
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
   ┌──────────┐    ┌──────────────┐   ┌──────────┐
   │ Web 前端 │    │ Python 后端  │   │ VS Code  │  ← 不变
   │ (现有)   │    │ (现有)       │   │ 桥 (现有)│
   └──────────┘    └──────────────┘   └──────────┘
```

#### 核心收益

| 收益 | 重要度 | 说明 |
|------|--------|------|
| 🖼️ 独立窗口 | ⭐⭐⭐⭐⭐ | 不被淹没在浏览器标签页，Alt+Tab 独立切换 |
| 📋 系统托盘 | ⭐⭐⭐⭐ | 后台运行不占任务栏，一键唤起 |
| 🔔 原生通知 | ⭐⭐⭐⭐ | 不在浏览器时也能收到任务完成通知 |
| 🚀 开机自启 | ⭐⭐⭐ | 登录后自动启动 |
| ⌨️ 全局快捷键 | ⭐⭐⭐ | `Ctrl+Shift+Z` 唤起对话窗口 |
| 📁 文件关联 | ⭐⭐ | 双击代码文件直接让祖龙分析 |
| 💾 独立体验 | ⭐⭐ | 不依赖浏览器，更像本地应用 |

### 4.3 方案 B：PWA（轻量备选）

通过添加 `manifest.json` + Service Worker，让浏览器"安装为应用"，获得独立窗口。

**优点**：零包体积，极低工程成本（~0.5 天）
**缺点**：无系统托盘、无开机自启、无全局快捷键、通知能力有限、依赖浏览器

可作为方案 A 的需求探针先行验证（对应 §7 Phase 0）：若 PWA 已能满足"独立窗口"诉求，可暂缓 Electron 投入。

### 4.4 方案 C：原生桌面（不推荐）

Win (C#/WPF) + Mac (Swift/SwiftUI) + Linux (GTK/Qt) 三端各写一套。

**工程量巨大**（数月），且需要重写 Web 前端 15600 行代码。仅在需要极致性能（如 60fps 3D 桌面宠物渲染）时才需要重新考虑。

## 5. Electron 三端适配分析

### 5.1 代码共享度

Electron 本身 = Chromium + Node.js 的跨平台运行时。**95%+ 的壳代码三端共享**。

需要平台差异处理的部分（~5%）：

| 适配点 | Windows | macOS | Linux |
|--------|---------|-------|-------|
| Python 启动 | `python.exe` / `pythonw.exe` | `python3` | `python3` |
| 系统托盘 | Tray API | Tray API（菜单行为略有差异） | Tray API |
| 开机自启 | 注册表 Run 键 | LaunchAgent plist | autostart `.desktop` |
| 全局快捷键 | globalShortcut API | 同上 + 辅助功能权限 | 同上 |
| 打包格式 | `.exe` (NSIS) | `.dmg` | `.AppImage` / `.deb` |
| 签名公证 | 可选代码签名 | 必须签名+公证 | 可选 |

### 5.2 打包配置

使用 `electron-builder`，一次配置三端打包：

```yaml
# electron-builder.yml
appId: com.zulong.desktop
productName: 祖龙

win:
  target: [{ target: nsis, arch: [x64] }]
  icon: assets/icon.ico

mac:
  target: [{ target: dmg, arch: [x64, arm64] }]
  icon: assets/icon.icns
  category: public.app-category.developer-tools

linux:
  target:
    - { target: AppImage, arch: [x64] }
    - { target: deb, arch: [x64] }
  icon: assets/icon.png
  category: Development
```

> **注意**：不能在 Windows 上打 macOS 包（反之亦然），需要 CI 矩阵。祖龙已有 `.github/workflows/platform-smoke.yml` 三端 runner 矩阵，但其内容仅为 Python + IDE 插件的**冒烟测试**（`smoke_platform.py` + `npm run smoke:platform`），**与 electron-builder 的打包/签名/发布无关**。可复用的只是三端 `runs-on` 运行环境，**Electron 打包流水线需新建**（建议新增 `.github/workflows/desktop-release.yml`）。

### 5.3 与 Python 后端三端适配的衔接

Python 后端已通过 TSD 第 25 章完成三端适配：

- `RuntimeEnvironment`（runtime_env.py）：检测 OS/Shell/路径风格
- 三端 `config/profiles/{windows|linux|macos}.yaml`
- VS Code 启动器三端化（`vscode_launcher.py`）
- 摄像头/音频后端三端选择器

桌面壳只需要把这一套从"手动 `python start.py`"升级为"双击图标自动启动"，底层跨平台能力已全部就绪。

### 6.2 不做的事（避免范围蔓延）

- ❌ 不改动 Web 前端代码
- ❌ 不改动 Python 后端代码
- ❌ 不重写任何业务逻辑
- ❌ 不在第一版做桌面宠物渲染
- ❌ 不在第一版做自动更新（可用 electron-updater 后续加）

### 6.3 运行时分发策略：Python + 依赖 + 模型 ⚠️

v1.0 将"用户未装 Python"作为低优先级风险一笔带过，但这是决定"双击图标就能用"能否达成的**头号瓶颈**，且远比 Electron 壳本身难。以下结论均基于对 `requirements*.txt` 与 `models/` 目录的实测核查（2026-06-27）。

> 📌 **总原则**：运行时分为**三层**，分别处理、各自独立——**Electron 壳只装壳，Python 依赖按平台装，模型按需下载/复制**。不要试图把三者打进一个安装包。

#### 6.3.1 三端依赖差异（实测）

祖龙**已经按平台拆分了 requirements**，桌面壳可直接复用：

```
requirements-core.txt        ← 三端共享（FastAPI/numpy/networkx/qdrant-client…）
requirements-ml-common.txt   ← 三端共享（torch/transformers/opencv/sentence-transformers）
requirements-audio.txt       ← 三端共享（kokoro/sherpa-onnx/funasr/pyaudio）
        │
        ├─ requirements-windows.txt  ──┐ 引用上面 3 个，再加：
        ├─ requirements-linux.txt    ──┤   onnxruntime-gpu + bitsandbytes + pynvml
        └─ requirements-macos.txt    ──┘ 仅 onnxruntime（CPU 版），❌ 不含 CUDA 包
```

**pip 语法三端一致**（都是 `pip install -r requirements-{平台}.txt`），差异在**包内容**：

| 差异点 | Windows | Linux | macOS |
|--------|---------|-------|-------|
| ONNX 加速 | `onnxruntime-gpu` | `onnxruntime-gpu` | `onnxruntime`（纯 CPU，**不可装 GPU 版**） |
| 量化库 | `bitsandbytes` | `bitsandbytes` | ❌ **不可用**（CUDA-only） |
| GPU 监控 | `pynvml` | `pynvml` | ❌ 无 |
| PyTorch wheel | CUDA wheel | CUDA wheel | **MPS wheel**（Apple Silicon 专用） |

> 🔧 **修正（v1.1）**：原稿难点表所列"FAISS / TensorFlow(YAMNet)"经核查**不在依赖中**——向量库实际为 `qdrant-client`，YAMNet 未落地依赖。真实的重型依赖为：`torch`、`onnxruntime-gpu`、`sherpa-onnx`、`funasr`、`bitsandbytes`、`sentence-transformers`。

> ⚠️ **隐藏坑——系统级原生依赖**：`requirements-audio.txt` 注释指出 `PyAudio` 依赖系统级 `PortAudio`，三端前置不同：
> - Windows：需匹配的预编译 wheel，否则 pip 构建失败
> - Linux：须先 `apt install portaudio19-dev python3-dev`
> - macOS：须先 `brew install portaudio`
>
> 这意味着即便用便携 Python，**系统库仍需用户或安装脚本额外处理**，是纯 pip 无法覆盖的环节。

#### 6.3.2 模型体积实测

`models/` 目录**总计 59 GB**，且已被 `.gitignore` 忽略（git 跟踪数 = 0），本就不随代码分发。但其中**真正核心的模型仅 ~4 GB**，其余是备选/历史/重复权重：

| 模型 | 角色 | 体积 | 必要性 |
|------|------|------|--------|
| ALBERT-tiny-chinese | L1-B 意图分类 | 17M | ✅ 核心 |
| bge-small-zh-v1.5 | Embedding 向量 | 184M | ✅ 核心 |
| SenseVoice-Small | ASR 主引擎 | 229M | ✅ 核心 |
| Kokoro-82M | TTS 主引擎 | 347M | ✅ 核心 |
| Qwen3.5-0.8B-AWQ | L2 备脑 | 945M | ✅ 核心 |
| Qwen3.5-2B-AWQ | L2 主脑（本地推理时） | 2.4G | ✅ 核心 |
| **核心小计** | | **~4.1 GB** | |
| CosyVoice3-0.5B | TTS 备选 | 9.1G | ❌ 可选 |
| OpenGVLab/InternVL | 视觉可选 | 3.6G | ❌ 可选 |
| unsloth / Qwen-4B / 历史 | 备份/重复 | ~30G+ | ❌ 不必分发 |

**关键结论**：模型**不可内嵌进安装包**（59GB 不可行，即使核心 4GB 也会拖垮 Electron 下载体验），但配置中引用的均为**相对路径**（`./models/...`），因此"独立打包 + 放对位置即可"是可行的。

#### 6.3.3 推荐的分层分发架构

```
┌─ 第 1 层：祖龙桌面壳（Electron .exe / .dmg / .AppImage）  ~150MB
│   └─ 仅含壳逻辑（窗口/托盘/快捷键/进程管理），不含 Python、不含模型
│
├─ 第 2 层：Python 依赖 → 按平台安装，不打进壳
│   └─ pip install -r requirements-{windows|macos|linux}.txt
│      （复用 6.3.1 的平台拆分；注意 PortAudio 等系统级前置）
│
└─ 第 3 层：模型 → 独立模型包 + 首启下载 / 手动复制
    ├─ 核心包（~4GB）：必装，预打为 zulong-models-core 压缩包，解压到 ./models/
    └─ 可选包（CosyVoice/视觉等）：按需下载，非必需
```

#### 6.3.4 Python 环境与整体策略选择

| 策略 | Python 环境 | 依赖 | 模型 | 工期量级 | 适用 |
|------|-----------|------|------|---------|------|
| **A. 开发/内部版** | 用户自备 | 用户跑平台脚本 | 手动复制 `models/` | ~2 周（仅壳） | MVP、开发者 |
| **B. 普通用户版（推荐）** | 便携 Python 内嵌 | 预装 + 系统库脚本 | **首启向导下载核心 4GB 包** | +2-4 周 | 面向普通用户首版 |
| **C. 终极一键版** | PyInstaller 整包 | 内嵌 | 内嵌或引导下载 | +1-2 月（ONNX/CUDA 三端调试坑多） | 远期目标 |

> 📌 **建议**：Phase 1 采用策略 A 快速验证壳可行性，明确标注"首版需预装 Python"；Phase 2 视反馈升级到策略 B；策略 C 作为远期目标，不进入首版工期承诺。无论哪种策略，**模型一律走"独立核心包 + 手动复制/首启下载"**，不内嵌。

## 8. 风险评估

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| Electron 包体积过大 (~150MB) | 用户下载体验 | 高 | 提供精简版（PWA）+ 标准版（Electron）双通道 |
| **Python 运行时分发**（v1.1 提级） | 用户未装 Python / 依赖缺失 → 无法"双击即用" | **高** | **首版策略 A（要求预装 Python + 一键脚本），Phase 2 升级到便携 Python；远期 PyInstaller**。详见 §6.3，切勿低估 |
| **模型体积过大**（v1.1 新增） | `models/` 实测 59GB，核心仍 ~4GB，内嵌不可行 | **高** | **三层分离**：壳不含模型；核心模型独立打包（~4GB）供首启下载或手动复制；可选模型按需下载。详见 §6.3.2/6.3.3 |
| **系统级原生依赖缺失**（v1.1 新增） | PyAudio 依赖 PortAudio：Win 需 wheel / Linux 需 `portaudio19-dev` / macOS 需 Homebrew | 中 | 提供平台安装脚本（Win 预置 wheel；Linux/macOS 装系统包）；便携 Python 也无法绕过此步 |
| Electron 安全配置不当 | 加载内容可控场景下的 RCE 风险 | 中 | 强制 `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`，用 `contextBridge` 暴露**最小** IPC 白名单；配置 CSP；禁用 remote 模块 |
| 后端子进程残留 / 端口冲突 | 用户已 `python start.py` 起了后端，壳又 spawn 一个；退出后进程残留 | 中 | 启动前探测 8090 端口，命中则连接既有实例而非重启；Windows 用 Job Object 绑定子进程树保证随壳退出 |
| macOS 签名公证 | 无法在 Mac App Store 外分发 | 中 | Phase 1 跳过，Phase 2 补齐 |
| 用户已有浏览器习惯 | 桌面壳使用率低 | 低 | 不影响现有 Web 途径，纯增量 |
| 维护负担 | 长期维护两套启动方式 | 低 | 壳层极薄，核心逻辑全在后端 |

## 9. 决策建议

| 问题 | 结论 |
|------|------|
| 值得做桌面端吗？ | ✅ 值得，但只做"壳"层 |
| 用 Electron 吗？ | ✅ 是，成本最低、三端适配最省 |
| 会破坏现有架构吗？ | ❌ 不会，完全解耦，不改现有代码 |
| 三个部署场景冲突吗？ | ❌ 不冲突，各取所需 |
| 工程量大吗？ | **壳层 ~3 周（13-18 人天）**；若含 Python 免安装分发则按 §6.3 策略叠加，**须先定策略再承诺工期** |
| 先做什么？ | Phase 1 MVP：Windows 端壳验证（策略 A，需预装 Python） |

### 9.1 前置决策项（Phase 1 启动前须拍板）🔴

| 待决策项 | 选项 | 对工期的影响 |
|---------|------|------------|
| 首版是否要求用户预装 Python？ | A 预装 / B 便携 Python / C PyInstaller | **~2 周 vs +2-4 周 vs +1-2 月**（见 §6.3.4） |
| 模型如何分发？（v1.1 新增） | 内嵌(不可行) / 独立核心包+手动复制 / 首启向导下载 | 决定首启体验与下载基建（见 §6.3.3） |

## 附录：关键技术决策记录

### A.1 为什么不用 Tauri？

Tauri（Rust 后端）包体积更小（~5MB），但：
- 团队无 Rust 经验，学习成本高
- Tauri 的进程管理 API 不如 Node.js 成熟
- Python 后端已承担所有计算，不需要 Tauri 的 Rust 性能优势
- Electron 的生态（electron-builder、auto-launch 等）更成熟

> 若未来需要极致性能的桌面宠物渲染，可在 Electron 壳中通过 IPC 调用 Rust 原生模块，无需整体迁移到 Tauri。

### A.2 为什么不是"祖龙专用浏览器"？

Chromium Embedded Framework (CEF) 或 WebView2 虽然更"像原生"，但：
- 失去了 Electron 生态的便利（打包、更新、托盘等开箱即用）
- 需要处理更多平台差异
- 本质上和 Electron 一样是"内嵌浏览器"

### A.3 与祖龙 VS Code 插件的关系

桌面端 ≠ 替代 VS Code 插件。两者互补：

- **桌面端**：主交互界面（聊天、任务、图谱、审批）
- **VS Code 插件**：后台执行桥（终端、文件编辑、命令执行）
- 桌面壳可以在用户需要时引导打开 VS Code 查看任务代码

这沿用了 TSD 第 23 章的设计原则："Web 端为主交互界面，VS Code 插件仅作为后台执行桥"。
