# 祖龙桌面端可行性分析报告

> 版本: v1.0
> 日期: 2026-06-27
> 状态: 设计评审中
> 作者: 架构组

---

## 1. 背景与动机

### 1.1 需求来源

用户反馈希望祖龙提供一个桌面端程序，而非仅通过浏览器访问。核心诉求包括：

- 独立的应用窗口，不被淹没在浏览器标签页中
- 系统级集成（托盘常驻、原生通知、全局快捷键）
- "双击图标就能用"的体验

### 1.2 评估目标

本文档旨在从技术架构、工程成本、用户体验三个维度评估桌面端的可行性和方案选型，避免盲目开发或重复造轮子。

---

## 2. 祖龙部署场景分析

祖龙有三种核心部署场景，桌面端需求仅覆盖其中一种：

| 场景 | 所需模块 | 界面形式 | 是否需要桌面端 |
|------|---------|---------|-------------|
| 🤖 **机器人端侧部署** | core + full（摄像头/麦克风/L1全套） | Web 远程监控后台 | ❌ 不需要 |
| 🖥️ **服务器端部署** | core（推理/记忆/工具） | Web 端 | ❌ 不需要 |
| 💻 **单机用户** | core + Web UI + VS Code 桥 | 希望是桌面应用 | ✅ 需要 |

**关键原则**：三种场景互不干扰，各取所需。桌面端只是为单机用户增加一种可选的启动方式，不改变现有任何架构。

### 2.1 当前架构的模块化支持

祖龙的 `ModuleManager`（[module_manager.py](../../zulong/launcher/module_manager.py)）已经通过 `mode_tags` 体系支持按场景组装模块：

```
mode_tags 体系:
  {"core"}     → 任何模式都启动（Config、MemoryGraph、InferenceEngine...）
  {"full"}     → 仅 Full 模式启动（摄像头、麦克风、L1-A反射、技能包...）
  {"optional"} → 可运行时动态开关

启动模式:
  IDE 模式 → core + Web UI + IDE 后台桥 → 单机用户 / 服务器部署
  Full 模式 → core + full + Web UI + IDE 后台桥 → 机器人端侧
```

> 详细架构说明参见 [祖龙模块化技术架构](../../AGENTS.md)。

## 3. WebSocket 通信分析

### 3.1 当前通信架构

```
┌──────────────────┐     WebSocket      ┌──────────────────┐
│  前端 (Web/IDE)  │ ◄────────────────► │  Python 后端     │
│                  │  ws://127.0.0.1:   │  (FastAPI)       │
│  - Web 聊天界面   │   8090/ws (Web端)  │                  │
│  - VS Code 插件  │   8090/ide (IDE端) │  - L1-B 调度     │
│  - 记忆图谱      │                    │  - L2 推理       │
│  - 审批面板      │  心跳: 30s         │  - MemoryGraph   │
│                  │  超时: 5s          │  - TaskGraph     │
│                  │  断连: 3次丢失     │  - FC 循环       │
└──────────────────┘                    └──────────────────┘
```

### 3.2 本地 WebSocket 的性能特征

| 通信方式 | 典型延迟 | 适用场景 |
|----------|---------|----------|
| 进程内函数调用 | ~纳秒 | 单体桌面应用 |
| 共享内存 (SharedMemory) | ~微秒 | 高频传感器数据（祖龙已有） |
| 本地 WebSocket (127.0.0.1) | ~0.1-1ms | 祖龙当前方案 |
| 远程 WebSocket | ~10-100ms+ | 云端通信 |

**结论**：本地 WebSocket 走 TCP loopback，操作系统内核对其有优化，延迟在 0.1-0.5ms。对于 LLM 推理（秒级），此开销可忽略不计。

### 3.3 潜在的瓶颈及应对

| 瓶颈 | 影响场景 | 已有应对方案 | 未来增强方向 |
|------|---------|------------|------------|
| JSON 序列化开销 | 30fps 实时渲染 | 大消息分片（TSD v2.9.5） | 二进制帧 + protobuf |
| 单连接串行化 | 音频流 + 文本流并发 | 双通道分离（/ws + /ide） | 多路复用 |
| 高频帧数据传输 | 桌面宠物动画 | 渲染本地化 + WebSocket 只发指令 | 指令通道模式 |
| 断线重连 | 网络不稳定 | PendingMessageCache 缓存 5 分钟 | 已满足需求 |

**核心设计原则**：高频渲染（动画帧、物理模拟）→ 纯本地处理；AI 决策（情绪、行为、对话）→ WebSocket 发指令；用户交互 → WebSocket 上报。这与祖龙 L0 设备层本地处理 + L1-L3 事件驱动的架构哲学完全一致。

## 4. 技术方案对比

### 4.1 方案总览

| 方案 | 工程量 | 三端适配 | 包体积 | 用户体验 | 推荐度 |
|------|--------|---------|--------|---------|--------|
| **A. Electron 壳** | ⭐⭐ 低 | 天然跨平台 | ~150MB | 接近原生 | ⭐⭐⭐⭐⭐ |
| B. PWA | ⭐ 极低 | 浏览器层 | 0 | 有限 | ⭐⭐⭐ |
| C. 原生桌面 | ⭐⭐⭐⭐⭐ 极高 | 三端各写 | ~30MB | 完美 | ⭐ (不推荐) |

### 4.2 方案 A：Electron 壳（推荐）

#### 架构

```
┌─────────────────────────────────────────────────────────┐
│              Zulong Desktop (Electron 壳)                 │
│                                                          │
│  ┌──────────────────────────────────────────────────┐   │
│  │  BrowserView / webview                           │   │
│  │  → 加载 http://127.0.0.1:8090                    │   │
│  │  → 复用 100% 现有 Web 前端 (index.html 15600行)   │   │
│  └──────────────────────────────────────────────────┘   │
│                                                          │
│  壳层能力 (新增，不改现有代码):                            │
│  ├── 进程管理: spawn("python start.py")                  │
│  ├── 系统托盘: Tray + 右键菜单 (显示/隐藏/退出)            │
│  ├── 原生通知: Notification API                          │
│  ├── 全局快捷键: globalShortcut.register("Ctrl+Shift+Z") │
│  ├── 开机自启: auto-launch                               │
│  ├── 单实例锁: app.requestSingleInstanceLock()           │
│  └── 窗口管理: 记住位置/大小、最小化到托盘                │
└─────────────────────────────────────────────────────────┘
```

#### 与现有架构的关系（完全解耦）

```
                    ┌──────────────┐
                    │  Desktop 壳  │  ← 新增 (可选用)
                    │  (Electron)  │
                    └──────┬───────┘
                           │ HTTP (localhost:8090)
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
   ┌──────────┐    ┌──────────────┐   ┌──────────┐
   │ Web 前端 │    │ Python 后端  │   │ VS Code  │  ← 不变
   │ (现有)   │    │ (现有)       │   │ 桥 (现有)│
   └──────────┘    └──────────────┘   └──────────┘
```

#### 核心收益

| 收益 | 重要度 | 说明 |
|------|--------|------|
| 🖼️ 独立窗口 | ⭐⭐⭐⭐⭐ | 不被淹没在浏览器标签页，Alt+Tab 独立切换 |
| 📋 系统托盘 | ⭐⭐⭐⭐ | 后台运行不占任务栏，一键唤起 |
| 🔔 原生通知 | ⭐⭐⭐⭐ | 不在浏览器时也能收到任务完成通知 |
| 🚀 开机自启 | ⭐⭐⭐ | 登录后自动启动 |
| ⌨️ 全局快捷键 | ⭐⭐⭐ | `Ctrl+Shift+Z` 唤起对话窗口 |
| 📁 文件关联 | ⭐⭐ | 双击代码文件直接让祖龙分析 |
| 💾 独立体验 | ⭐⭐ | 不依赖浏览器，更像本地应用 |

### 4.3 方案 B：PWA（轻量备选）

通过添加 `manifest.json` + Service Worker，让浏览器"安装为应用"，获得独立窗口。

**优点**：零包体积，极低工程成本（~0.5 天）
**缺点**：无系统托盘、无开机自启、无全局快捷键、通知能力有限、依赖浏览器

可作为方案 A 的 MVP 先行版本快速验证需求。

### 4.4 方案 C：原生桌面（不推荐）

Win (C#/WPF) + Mac (Swift/SwiftUI) + Linux (GTK/Qt) 三端各写一套。

**工程量巨大**（数月），且需要重写 Web 前端 15600 行代码。仅在需要极致性能（如 60fps 3D 桌面宠物渲染）时才需要重新考虑。

## 5. Electron 三端适配分析

### 5.1 代码共享度

Electron 本身 = Chromium + Node.js 的跨平台运行时。**95%+ 的壳代码三端共享**。

需要平台差异处理的部分（~5%）：

| 适配点 | Windows | macOS | Linux |
|--------|---------|-------|-------|
| Python 启动 | `python.exe` / `pythonw.exe` | `python3` | `python3` |
| 系统托盘 | Tray API | Tray API（菜单行为略有差异） | Tray API |
| 开机自启 | 注册表 Run 键 | LaunchAgent plist | autostart `.desktop` |
| 全局快捷键 | globalShortcut API | 同上 + 辅助功能权限 | 同上 |
| 打包格式 | `.exe` (NSIS) | `.dmg` | `.AppImage` / `.deb` |
| 签名公证 | 可选代码签名 | 必须签名+公证 | 可选 |

### 5.2 打包配置

使用 `electron-builder`，一次配置三端打包：

```yaml
# electron-builder.yml
appId: com.zulong.desktop
productName: 祖龙

win:
  target: [{ target: nsis, arch: [x64] }]
  icon: assets/icon.ico

mac:
  target: [{ target: dmg, arch: [x64, arm64] }]
  icon: assets/icon.icns
  category: public.app-category.developer-tools

linux:
  target:
    - { target: AppImage, arch: [x64] }
    - { target: deb, arch: [x64] }
  icon: assets/icon.png
  category: Development
```

> **注意**：不能在 Windows 上打 macOS 包（反之亦然），需要 CI 矩阵。祖龙已有 `.github/workflows/platform-smoke.yml` 三端 CI 基础，可直接复用。

### 5.3 与 Python 后端三端适配的衔接

Python 后端已通过 TSD 第 25 章完成三端适配：

- `RuntimeEnvironment`（runtime_env.py）：检测 OS/Shell/路径风格
- 三端 `config/profiles/{windows|linux|macos}.yaml`
- VS Code 启动器三端化（`vscode_launcher.py`）
- 摄像头/音频后端三端选择器

桌面壳只需要把这一套从"手动 `python start.py`"升级为"双击图标自动启动"，底层跨平台能力已全部就绪。

## 6. 工程估算

### 6.1 开发任务分解

| 任务 | 预估工时 | 说明 |
|------|---------|------|
| Electron 壳基础框架 | 2-3 天 | main process + preload + webview |
| 后端进程生命周期管理 | 1 天 | spawn/pythonw 无窗口启动、健康检查、优雅关闭 |
| 系统托盘 + 上下文菜单 | 0.5 天 | Tray API |
| 原生通知桥接 | 0.5 天 | Notification API + Web→Main IPC |
| 全局快捷键 | 0.5 天 | globalShortcut API |
| 开机自启 | 0.5 天 | auto-launch 包 |
| 单实例锁 | 0.5 天 | app.requestSingleInstanceLock() |
| 窗口状态记忆 | 0.5 天 | 位置/大小持久化 |
| Windows 打包 (.exe) | 1 天 | electron-builder + NSIS |
| macOS 打包 (.dmg) | 1 天 | electron-builder + 签名公证配置 |
| Linux 打包 (.AppImage) | 1 天 | electron-builder |
| 三端测试 + CI | 2 天 | 复用现有 CI matrix |
| **合计** | **10-15 人天** | |

### 6.2 不做的事（避免范围蔓延）

- ❌ 不改动 Web 前端代码
- ❌ 不改动 Python 后端代码
- ❌ 不重写任何业务逻辑
- ❌ 不在第一版做桌面宠物渲染
- ❌ 不在第一版做自动更新（可用 electron-updater 后续加）

## 8. 风险评估

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| Electron 包体积过大 (~150MB) | 用户下载体验 | 高 | 提供精简版（PWA）+ 标准版（Electron）双通道 |
| Python 环境依赖 | 用户未安装 Python | 中 | 提示安装；后续可考虑 PyInstaller 打包 |
| macOS 签名公证 | 无法在 Mac App Store 外分发 | 中 | Phase 1 跳过，Phase 2 补齐 |
| 用户已有浏览器习惯 | 桌面壳使用率低 | 低 | 不影响现有 Web 途径，纯增量 |
| 维护负担 | 长期维护两套启动方式 | 低 | 壳层极薄，核心逻辑全在后端 |

| 问题 | 结论 |
|------|------|
| 值得做桌面端吗？ | ✅ 值得，但只做"壳"层 |

## 附录：关键技术决策记录

### A.1 为什么不用 Tauri？

Tauri（Rust 后端）包体积更小（~5MB），但：
- 团队无 Rust 经验，学习成本高
- Tauri 的进程管理 API 不如 Node.js 成熟
- Python 后端已承担所有计算，不需要 Tauri 的 Rust 性能优势
- Electron 的生态（electron-builder、auto-launch 等）更成熟

> 若未来需要极致性能的桌面宠物渲染，可在 Electron 壳中通过 IPC 调用 Rust 原生模块，无需整体迁移到 Tauri。

### A.2 为什么不是"祖龙专用浏览器"？

Chromium Embedded Framework (CEF) 或 WebView2 虽然更"像原生"，但：
- 失去了 Electron 生态的便利（打包、更新、托盘等开箱即用）
- 需要处理更多平台差异
- 本质上和 Electron 一样是"内嵌浏览器"

### A.3 与祖龙 VS Code 插件的关系

桌面端 ≠ 替代 VS Code 插件。两者互补：

- **桌面端**：主交互界面（聊天、任务、图谱、审批）
- **VS Code 插件**：后台执行桥（终端、文件编辑、命令执行）
- 桌面壳可以在用户需要时引导打开 VS Code 查看任务代码

这沿用了 TSD 第 23 章的设计原则："Web 端为主交互界面，VS Code 插件仅作为后台执行桥"。
