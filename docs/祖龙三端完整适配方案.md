# 祖龙三端完整适配方案

> 目标平台：Windows / Linux / macOS  
> 评估日期：2026-05-29  
> 适用范围：Zulong IDE、Python 后端、Web/WebSocket、L0-L3 本地完整能力、模型后端、音视频设备、安装部署与验收

## 1. 结论摘要

祖龙当前已经具备一部分跨平台基础，尤其是 `cuda/mps/cpu` 设备选择已经落入 `zulong/utils/device.py`，L1A/L1B/L2 配置、Embedding、光流、部分音频路径已经开始复用该设备选择能力。因此三端适配不是从零开始。

但如果目标是“完整能力三端适配”，剩余工作仍为中等偏大。主要工作不应改变 TSD 规定的四层主架构，而应补齐平台适配层、依赖矩阵、设备层抽象、模型后端降级策略和三端验收流水线。

建议按“三阶段”推进：

| 阶段 | 目标 | 预计周期 | 结果 |
| --- | --- | --- | --- |
| P0 | 三端基础运行闭环 | 2-3 周 | IDE/Web 后端、L2 云端/Ollama、记忆、任务、工具执行可跑 |
| P1 | 三端本地感知能力 | 3-5 周 | 摄像头、麦克风、扬声器、ASR/TTS 按平台可用并可降级 |
| P2 | 三端完整本地模型能力与发布验收 | 3-5 周 | 平台 profile、安装器、CI/冒烟测试、文档与诊断工具完善 |

完整适配预计总周期：5-8 周可达到稳定可用；8-10 周可达到较完整的自动诊断、发布与一致体验。

## 2. TSD 对齐原则

本方案严格保持 TSD 的总体架构不变：

- L0 设备层仍负责摄像头、麦克风、扬声器、传感器和运动控制。
- L1 仍保持 L1-A 反射、L1-B 调度与意图守门、L1-C 视觉、L1-D 听觉、L1-E 安全。
- L2 仍负责认知推理、FC 循环、TaskGraph、MemoryGraph、CircuitBreaker。
- L3 仍为专家模型池与 TTS/视觉/导航/操作专家。
- EventBus、SharedMemory、WebSocket、MemoryGraph、TaskGraph 不因三端适配改变职责。

三端适配只允许在以下方向做工程补齐：

- 平台检测与配置 profile。
- 设备驱动后端选择。
- 模型推理后端选择与降级。
- 依赖安装矩阵。
- 启动脚本、诊断脚本、验收脚本。
- 对 L2 工具提示注入当前 OS/Shell 信息。

禁止为了适配平台而绕过 L1-B 主链、绕过 EventBus、在 L2 之外硬编码回答、或把 L0 设备逻辑直接塞入 L2。

## 3. 当前已完成基础

### 3.1 加速器抽象

已存在跨平台设备选择：

- `zulong/utils/device.py`
  - `resolve_device("auto")`：优先 CUDA，其次 MPS，最后 CPU。
  - `torch_device()`：返回 PyTorch device。
  - `accelerator_info()`：返回平台、架构、CUDA/MPS 状态。
  - `empty_accelerator_cache()`：同时处理 CUDA 与 MPS cache。

已接入的代表模块：

- `zulong/l1a/l1a_config.py`
- `zulong/l1b/l1b_config.py`
- `zulong/l2/l2_config.py`
- `zulong/l0/gpu_optical_flow.py`
- `zulong/memory/embedding_manager.py`
- `zulong/ide/audio_handler.py`

### 3.2 macOS MPS 基础

`zulong/adapters/model_loader.py` 已能识别 Apple Silicon：

- CUDA 不可用但 MPS 可用时返回 `HardwareType.APPLE_SILICON`。
- 模型配置里已有 `Qwen2.5-3B-Instruct-MPS` 命名。

`zulong/l0/gpu_optical_flow.py` 已支持 `mps`，并在失败时回退 CPU。

### 3.3 VS Code 插件跨平台基础

`zulong-ide` 本体继承 VS Code/Node 跨平台基础，且已有部分平台判断：

- `zulong-ide/src/utils/shell.ts`
- `zulong-ide/src/utils/path.ts`
- `zulong-ide/src/utils/process-termination.ts`

插件侧不是最大阻塞点，重点在 Python 后端和本地模型/设备能力。

## 4. 平台能力目标矩阵

### 4.1 总体能力矩阵

| 能力 | Windows | Linux | macOS |
| --- | --- | --- | --- |
| Zulong IDE 插件 | 必须支持 | 必须支持 | 必须支持 |
| Web/WebSocket 后端 | 必须支持 | 必须支持 | 必须支持 |
| MemoryGraph/TaskGraph/FC | 必须支持 | 必须支持 | 必须支持 |
| L2 云端模型 | 必须支持 | 必须支持 | 必须支持 |
| Ollama 本地模型 | 推荐支持 | 推荐支持 | 推荐支持 |
| vLLM/SGLang | CUDA/WSL2 可选 | CUDA 推荐 | 不作为默认目标 |
| llama.cpp | 可选 | 可选 | 推荐 |
| MLX | 不适用 | 不适用 | 可选增强 |
| PyTorch CUDA | NVIDIA 可用 | NVIDIA 可用 | 不适用 |

| 摄像头 | DirectShow/MSMF | V4L2 | AVFoundation |
| 麦克风/扬声器 | PortAudio/PyAudio | ALSA/Pulse/PipeWire + PortAudio | CoreAudio + PortAudio |

### 4.2 macOS 能力边界

macOS 不应强求与 Linux CUDA 服务同形。macOS 的推荐模型路径：

1. L2 默认 `ollama` 或 `llamacpp`。
2. Apple Silicon 本地 PyTorch 模型使用 MPS。
3. Whisper fallback 可使用 MPS。
4. SenseVoice ONNX 先以 CPU 为稳定目标。
5. vLLM/SGLang 不作为 macOS 默认验收项。

## 5. 模块改造清单

### 5.1 配置与平台 Profile

问题：

- `config/zulong_config.yaml` 中存在 `/mnt/d/...`、`D:/AI/workspace` 等固定路径。
- `.env.example` 中也有 WSL/Windows 绑定路径。
- 当前只有环境覆盖，没有显式平台 profile。

涉及文件：

- `config/zulong_config.yaml`
- `config/.env.example`
- `config/load_env.bat`
- `zulong/config/config_manager.py`

改造方案：

1. 新增平台 profile：
   - `config/profiles/windows.yaml`
   - `config/profiles/linux.yaml`
   - `config/profiles/macos.yaml`
2. `ConfigManager` 增加平台自动探测：
   - `platform.system()` 为 `Windows/Linux/Darwin`。
   - 支持 `ZULONG_PLATFORM_PROFILE` 强制指定。
3. 配置加载顺序调整为：
   - 基础配置 `zulong_config.yaml`
   - 环境配置 `environments.{env}`
   - 平台 profile
   - 环境变量覆盖
4. 所有模型路径改为：
   - `${ZULONG_HOME:./}`
   - `${ZULONG_MODEL_BASE_DIR:./models}`
   - 相对路径由 `Path` 在运行时解析。
5. 工作区默认值改为用户目录下安全路径：
   - Windows: `%USERPROFILE%/Zulong/workspace`
   - Linux/macOS: `~/Zulong/workspace`

验收标准：

- 三端启动时打印当前 profile、OS、Shell、模型目录、数据目录。
- 不设置任何环境变量时，三端均能加载默认配置。
- `rg "/mnt/d|D:/AI|BaiduNetdisk" config zulong` 不应在运行配置默认路径中命中。

### 5.2 Python 依赖矩阵

问题：

- 单一 `requirements.txt` 同时包含 `bitsandbytes`、`onnxruntime-gpu`、`pyaudio`。
- macOS 对 `onnxruntime-gpu`、`bitsandbytes`、部分音频依赖不友好。
- Linux 需要系统包，Windows 需要 wheel/运行库，macOS 需要 brew 依赖。

涉及文件：

- `requirements.txt`
- `README.md`
- `docs/guides/configuration.md`
- 新增安装脚本

改造方案：

拆分依赖：

| 文件 | 内容 |
| --- | --- |
| `requirements-core.txt` | FastAPI、uvicorn、pydantic、numpy、PyYAML、requests、MemoryGraph/TaskGraph 基础依赖 |
| `requirements-ml-common.txt` | torch、transformers、sentence-transformers、opencv-python、Pillow |
| `requirements-audio.txt` | soundfile、openai-whisper、kokoro、edge-tts、imageio-ffmpeg |
| `requirements-windows.txt` | onnxruntime-gpu 可选、pyaudio wheel 指引、CUDA 相关可选项 |
| `requirements-linux.txt` | onnxruntime-gpu 可选、pyaudio、系统包说明 |
| `requirements-macos.txt` | onnxruntime CPU、MPS PyTorch、避免 bitsandbytes/onnxruntime-gpu |
| `requirements-dev.txt` | pytest、pytest-asyncio、pytest-cov |

安装入口：

- `scripts/install_windows.ps1`
- `scripts/install_linux.sh`
- `scripts/install_macos.sh`
- `scripts/doctor.py`

验收标准：

- Windows/Linux/macOS 分别能完成 core install。
- macOS 安装不拉取 `onnxruntime-gpu` 和 `bitsandbytes`。
- Linux 安装脚本提示 `portaudio19-dev`、`ffmpeg`、`libgl1` 等系统依赖。
- macOS 安装脚本提示 `brew install portaudio ffmpeg`。

### 5.3 L0 摄像头适配

问题：

- `zulong/l0/devices/camera_device.py` 和 `zulong/l0/usb_camera.py` 使用 Windows DirectShow。
- 曝光、增益、白平衡参数没有按平台隔离。

涉及文件：

- `zulong/l0/devices/camera_device.py`
- `zulong/l0/usb_camera.py`
- `zulong/config/camera_config.py`
- `config/zulong_config.yaml`

改造方案：

1. 新增摄像头后端解析：
   - Windows: `CAP_DSHOW`, `CAP_MSMF`, `CAP_ANY`
   - Linux: `CAP_V4L2`, `CAP_ANY`
   - macOS: `CAP_AVFOUNDATION`, `CAP_ANY`
2. 抽出 `CameraBackendSelector`：
   - 文件建议：`zulong/l0/devices/camera_backend.py`
   - 提供 `get_camera_backends()`、`safe_set_camera_property()`。
3. 配置中增加：
   - `vision.camera.backend: auto`
   - `vision.camera.scan_range: 0..9`
   - `vision.camera.platform_properties`
4. 对曝光等属性做平台可用性检测，不把失败作为初始化失败。
5. 摄像头诊断：
   - 新增 `scripts/doctor_camera.py`
   - 输出设备列表、后端、实际分辨率、读取帧是否成功。

验收标准：

- Windows 能用 DirectShow/MSMF 打开摄像头。
- Linux 能用 V4L2 打开 `/dev/video*` 对应设备。
- macOS 能用 AVFoundation 或 `CAP_ANY` 打开默认摄像头。
- 不存在摄像头时，L0 初始化失败不拖垮 Web/IDE 主服务。

### 5.4 L0 音频设备适配

问题：

- 麦克风/扬声器使用 PyAudio，理论跨平台，但安装和设备索引差异大。
- macOS 需要麦克风权限提示。
- Linux 可能存在 ALSA/Pulse/PipeWire 差异。

涉及文件：

- `zulong/l0/devices/microphone_device.py`
- `zulong/l0/devices/speaker_device.py`
- `zulong/ide/audio_handler.py`
- `config/zulong_config.yaml`

改造方案：

1. 新增音频设备枚举工具：
   - 文件建议：`zulong/l0/devices/audio_backend.py`
   - 输出 input/output 设备、默认设备、采样率能力。
2. `device_index: null` 时使用默认设备，但记录实际设备名。
3. macOS 初始化失败时给出权限提示：
   - System Settings -> Privacy & Security -> Microphone。
4. Linux 初始化失败时给出 PortAudio/PulseAudio/PipeWire 提示。
5. Web 音频流继续走 `ffmpeg` 转码，但安装脚本确保 ffmpeg 存在。

验收标准：

- 三端均能列出音频输入/输出设备。
- 无设备或无权限时，系统返回可读诊断，不影响文本聊天。
- Web 端音频上传能在三端转换为 16k mono wav。

### 5.5 L1-D ASR 适配

问题：

- SenseVoice ONNX 的 `provider` 目前只区分 `cuda/cpu`。
- `resolve_device()` 可能返回 `mps`，但 sherpa-onnx 不使用 MPS provider。
- Whisper fallback 可在 macOS 上走 MPS，但需要显式支持。

涉及文件：

- `zulong/models/audio_model_container.py`
- `zulong/ide/audio_handler.py`
- `zulong/plugins/voice/l1d_audio_plugin.py`

改造方案：

1. 增加 `resolve_asr_provider()`：
   - `cuda -> cuda`
   - `mps -> cpu` for SenseVoice
   - `cpu -> cpu`
2. SenseVoice 初始化日志明确：
   - requested device
   - actual provider
   - fallback reason
3. Whisper fallback 使用 `resolve_device()`，macOS 允许 MPS。
4. 配置增加：
   - `audio.asr.sensevoice_provider: auto`
   - `audio.asr.whisper_device: auto`
   - `audio.asr.fallback_order: [sensevoice, whisper]`
5. 模型不存在时不报硬失败，降级为 Whisper 或 ASR unavailable。

验收标准：

- Windows/Linux CUDA 机器可用 SenseVoice CUDA。
- macOS 可用 SenseVoice CPU 或 Whisper MPS fallback。
- 模型缺失时系统能启动，并在首次语音请求返回明确错误。

### 5.6 L3 TTS 适配

问题：

- Kokoro/edge-tts 较容易跨平台。
- CosyVoice 相关文件硬编码 `D:\BaiduNetdiskDownload\...`。

涉及文件：

- `zulong/l3/tts_expert_node.py`
- `zulong/l3/tts_cosyvoice_wrapper.py`
- `zulong/l3/tts_cosyvoice_server.py`
- `zulong/l3/tts_cosyvoice_direct.py`
- `zulong/l3/tts_cosyvoice_gradio.py`
- `zulong/tts/cosyvoice_config.py`

改造方案：

1. Kokoro 作为三端默认 TTS。
2. edge-tts 作为网络 fallback。
3. CosyVoice 设为可选专家，不作为 P0/P1 阻塞项。
4. 移除 CosyVoice 默认参数中的本机绝对路径：
   - 统一从 `audio.tts.cosyvoice.*` 或 `ZULONG_COSYVOICE_*` 读取。
5. CosyVoice 不可用时返回 `capability_unavailable`，不影响文本输出。

验收标准：

- 三端无 CosyVoice 时仍可启动。
- Kokoro 可用时本地 TTS 正常。
- edge-tts 网络可用时可 fallback。

### 5.7 L2 本地模型后端适配

问题：

- vLLM/SGLang 当前偏 Linux CUDA/Windows WSL2。
- macOS 应走 Ollama/llama.cpp/MLX/MPS，而不是默认 vLLM。
- 配置里 `model_id` 存在 `/mnt/d/...` 固定路径。

涉及文件：

- `zulong/l2/inference_engine.py`
- `zulong/adapters/model_loader.py`
- `config/zulong_config.yaml`
- `scripts/start_vllm_wsl2_2b_awq.bat`
- `scripts/start_l2_backup_vllm.sh`

改造方案：

平台默认后端：

| 平台 | 默认 | 高性能可选 | 备注 |
| --- | --- | --- | --- |
| Windows | Ollama | WSL2 vLLM / llama.cpp | vLLM 通过 WSL2 profile |
| Linux | Ollama | vLLM / SGLang / llama.cpp | NVIDIA CUDA 推荐 vLLM |
| macOS | Ollama | llama.cpp / MLX | Apple Silicon 推荐 MPS/Metal |

代码调整：

1. 增加 `ModelBackendResolver`：
   - 文件建议：`zulong/adapters/backend_resolver.py`
   - 输入平台、GPU、配置，输出后端、base_url、model_id、限制说明。
2. `inference_engine.py` 不直接假设 vLLM 命名。
3. `model_loader.py` 中 `_init_vllm_engines()` 对 macOS 直接禁用或提示。
4. 增加 macOS `llamacpp` 与可选 `mlx` profile。

验收标准：

- 三端默认配置均能用 Ollama 或云端模型跑通 L2。
- Linux CUDA 可切 vLLM。
- Windows 可通过 WSL2 profile 切 vLLM。
- macOS 不因 vLLM 不可用导致系统失败。

### 5.8 工具执行与 Shell 提示适配

问题：

- `exec_tools.py`、`intent_prompt_builder.py`、`ide_prompt_handler.py` 有 Windows/PowerShell 固定提示。
- 这会导致祖龙在 Linux/macOS 上生成错误命令。

涉及文件：

- `zulong/tools/exec_tools.py`
- `zulong/l2/intent_prompt_builder.py`
- `zulong/ide/ide_prompt_handler.py`
- `zulong/tools/system_tools.py`

改造方案：

1. 新增 runtime environment detector：
   - 文件建议：`zulong/utils/runtime_env.py`
   - 输出 `os_name`、`shell_name`、`path_style`、`preferred_commands`、`forbidden_patterns`。
2. `exec_run_command` 的 schema 描述动态生成：
   - Windows: PowerShell/CMD 示例。
   - Linux/macOS: bash/zsh 示例。
3. Unix-only 拦截只在 Windows 启用。
4. Windows-only 命令也应在 Linux/macOS 提示替代。
5. 安全白名单按平台拆分：
   - common
   - windows
   - unix
6. L2 prompt 注入当前平台，不再写死 Windows。

验收标准：

- Windows 生成 PowerShell/CMD 合理命令。
- Linux/macOS 生成 bash/zsh 合理命令。
- 三端 `exec_run_command` 能执行 `python --version`、`node --version`、`git status`。

### 5.9 VS Code / IDE 桥适配

问题：

- `zulong/workspace/vscode_launcher.py` 主要探测 Windows 常见路径。
- Linux/macOS 只依赖 `shutil.which("code")`，缺少 GUI fallback。

涉及文件：

- `zulong/workspace/vscode_launcher.py`
- `config/zulong_config.yaml`

改造方案：

1. Windows:
   - 保留当前 `code.cmd`、`Code.exe` 探测。
2. Linux:
   - `code`
   - `codium`
   - `cursor`
3. macOS:
   - `code`
   - `/Applications/Visual Studio Code.app/.../bin/code`
   - `/Applications/Cursor.app/.../bin/cursor`
   - fallback: `open -a "Visual Studio Code" <path>`
4. `is_vscode_available()` 不应只依赖 `shutil.which()`，因为绝对路径也可用。

验收标准：

- 三端可打开项目目录。
- 未安装 VS Code 时返回可读提示，不影响任务在工作区写文件。

## 7. 阶段实施计划

### P0：三端基础运行闭环

目标：不要求所有设备和本地模型都启用，但三端都能启动、聊天、使用记忆、执行基础任务。

任务：

1. 拆分依赖文件。
2. 新增平台 profile。
3. 修复配置硬编码路径。
4. 修复 L2 prompt 和 exec tools 的 OS/Shell 注入。
5. VS Code launcher 补 Linux/macOS。
6. 新增 `scripts/doctor.py`。
7. 三端跑通：
   - FastAPI/WebSocket
   - L2 Ollama 或云端模型
   - MemoryGraph/TaskGraph
   - 基础文件工具

P0 验收：

```bash
python scripts/doctor.py
python -m zulong.ide.ide_server
pytest tests/platform/test_core_startup.py
```

### P1：三端感知与语音能力

目标：摄像头、麦克风、扬声器、ASR/TTS 在三端可用或可清晰降级。

任务：

1. 摄像头后端选择器。
2. 音频设备枚举与权限诊断。
3. SenseVoice provider 映射。

## 9. 风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| macOS 无 vLLM | 本地高性能 L2 不一致 | macOS 默认 Ollama/llama.cpp/MLX，不以 vLLM 为验收项 |
| `bitsandbytes` macOS 不可用 | 安装失败 | macOS requirements 排除，改用 MPS/CPU/Ollama |
| PyAudio 安装复杂 | 音频设备不可用 | 平台安装脚本 + doctor 诊断 + Web 音频不阻塞文本 |
| 摄像头权限差异 | L1-C 不可用 | 平台后端选择 + 权限提示 + graceful degradation |
| SenseVoice MPS 不支持 | macOS ASR GPU 不可用 | SenseVoice CPU + Whisper MPS fallback |
| 本机硬编码路径残留 | 三端启动失败 | profile 化 + CI grep 检查 |
| L2 生成错误 shell 命令 | 工具执行失败 | runtime_env 注入 + 平台白名单 |

## 12. 最终判断

当前代码已经完成约 30%-40% 的三端适配基础，主要体现在 MPS/CPU/CUDA 设备抽象和部分模块接入。剩余 60% 左右集中在依赖、配置、设备后端、ASR/TTS、LLM 后端 profile、命令执行提示和验收工具。

整体不需要重构 TSD 四层架构；正确做法是在各层边界补平台适配：

- L0：设备后端适配。
- L1：感知/听觉/视觉插件按平台降级。
- L2：模型后端和工具命令按平台选择。
- L3：专家模型路径和 TTS 能力配置化。
- 基础设施：配置、安装、doctor、测试矩阵。

这样可以在不偏离 TSD 的前提下，实现 Windows、Linux、macOS 三端完整适配。
