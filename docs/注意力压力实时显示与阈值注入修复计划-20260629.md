# 注意力压力实时显示与阈值注入修复计划（2026-06-29）

## 目标

把注意力压力链路拆成两个互不混淆的通道：

1. **前端实时显示通道**：每次模型调用返回后，只要拿到真实 `prompt_tokens` 或本地估算压力变化，就应通过 `attention.update` / `ATTENTION_UPDATE` 推送到 Web 面板，让用户实时看到当前上下文压力。
2. **LLM 阈值注入通道**：只有压力达到 yellow / red 阈值时，才把计算后的压力百分比和注意力选择提示注入给 LLM；green 状态不得把压力百分比实时塞给模型。

换句话说：**压力要实时显示给人看，但不要实时喂给模型；模型只在需要切换注意力时才看到压力提示。**

## 术语边界

| 名称 | 面向对象 | 含义 | 是否每轮发生 |
|---|---|---|---|
| `attention.update` | 后端内部事件 / Web 转发源 | 后端发出的注意力状态更新消息 | 可以每次模型返回后发生 |
| `ATTENTION_UPDATE` | WebSocket 前端事件 | Web 页面收到的注意力状态更新 | 可以每次模型返回后发生 |
| 前端压力显示 | 用户 | Web 面板展示 `provider_prompt_tokens`、`provider_context_pressure_percent`、压力颜色等 | 需要实时刷新 |
| LLM 压力注入 | 模型 | 在 provider messages 前临时 prepend 的压力提示 | 仅 yellow / red 阈值触发 |
| `provider_prompt_tokens` | 运行态遥测 | provider 返回的真实输入 token 数 | provider 返回 usage 后更新 |
| `provider_context_pressure_percent` | 运行态遥测 | `provider_prompt_tokens / threshold_budget_tokens × 100%` | provider 返回 usage 后更新 |

## 当前判断

### 已符合设计的部分

- 绿色压力不再注入 LLM，避免模型每轮被压力数字干扰。
- 注意力模式不变时不重复注入模式说明。
- 无 MemoryGraph / BFS 检索时不反复推送 `0` 值。
- 导航地图只在真实焦点变化、压力切换或恢复场景中注入，不再每轮塞地图。

### 需要修复的断点

1. **真实 provider usage 没有稳定进入前端实时显示**
   - 模型返回后，后端已经能拿到 `prompt_tokens`。
   - 注意力窗口也能记录该值。
   - 但 Full Web/Core FC 路径的稀疏 `attention.update` 主要按模式、压力层级、BFS、导航地图变化推送；当压力仍是 green 或模式未变时，`provider_prompt_tokens` / `provider_context_pressure_percent` 可能不会被推到 Web。

2. **前端主压力数字没有优先使用 provider 实际压力**
   - Web 路由已经预留 provider 字段。
   - 前端也能接收 provider 字段。
   - 但主压力标签仍优先使用 `trigger_budget_usage`、`context_pressure` 等旧字段；如果只收到 provider 压力，界面可能仍显示 `0%` 或旧值。

3. **阈值预算口径已裁决为完整上下文窗口**
   - Web 端已经可以设置 LLM 上下文窗口，该窗口就是动态注意力压力预算。
   - `threshold_budget_ratio=0.50` 属于历史压测/临时调低机制，不再作为系统默认机制保留。
   - 兼容字段如 `threshold_budget_ratio` 如仍存在，运行态应固定为 `1.0` 或仅作兼容遥测，不得再把压力预算折半。

## 修复原则

### 1. 前端实时显示必须独立于 LLM 注入

`attention.update` / `ATTENTION_UPDATE` 是用户界面遥测，不等于 LLM prompt 注入。

后端每次 provider 调用返回 usage 后，应至少更新：

```json
{
  "provider_prompt_tokens": 14008,
  "provider_context_pressure_percent": 21.4,
  "provider_usage_source": "provider",
  "registered_context_pressure": 0.0,
  "active_context_token_estimate": 0,
  "pressure_tier": "green"
}
```

即使 `pressure_tier` 仍是 `green`，也应允许前端实时显示这些数字。

### 2. LLM 只在 yellow / red 时看到压力提示

构建本轮发给 LLM 的 active context 时，继续遵守现有门禁：

- green：不注入压力百分比。
- yellow：首次达到阈值时注入注意力选择提示。
- red：按两阶段策略处理，必要时进入受限恢复。
- 注入给 LLM 的内容只包含计算后的压力百分比和行动提示，不注入原始窗口占比、阈值公式或多套百分比。

### 3. 稀疏推送不是“少推关键压力”

稀疏推送应该减少无意义噪音，例如 BFS 未发生时不刷 `0`、导航地图未变时不重复发。

但 provider usage 属于关键实时遥测，不能因为模式没变、压力没跨 yellow/red、BFS 没发生就被跳过。

## 建议代码落点

| 链路 | 文件 | 调整意图 |
|---|---|---|
| provider usage 回填 | `zulong/l2/fc_nodes.py` | 模型返回 usage 后，记录 `prompt_tokens`，并触发或标记一次前端遥测更新 |
| 单次决策 usage 回填 | `zulong/l2/inference_engine.py` | 非 FC 模型调用也要同样触发 provider usage 遥测 |
| 注意力事件生成 | `zulong/l2/inference_engine.py` | `_send_attention_update(...)` 增加 provider usage / active pressure 的独立 diff 维度 |
| Web 转发 | `zulong/launcher/web_chat_router.py` | 保持透传 provider 字段，必要时补 `provider_usage_source` |
| 前端显示 | `zulong_web/static/index.html` | 主压力标签优先使用 `provider_context_pressure_percent`，没有 provider usage 时再退回本地估算 |
| 阈值预算 | `zulong/l2/attention_window.py`、`zulong/l2/pressure_detector.py`、`config/zulong_config.yaml` | 统一为 Web 可配置的完整 LLM 上下文窗口；`threshold_budget_ratio` 仅保留兼容值 `1.0` |

## 验收要求

### 单元回归

- provider usage 返回后，即使压力为 green，也会产生可见遥测或可被下一帧前端状态读取。
- green 状态不会把压力百分比注入 LLM。
- yellow / red 状态才注入压力提示，并使用计算后的压力百分比。
- 前端压力主标签优先展示 `provider_context_pressure_percent`。

### 真实 Full 回归

1. 启动 `start.py` 并进入 Full mode。
2. 通过 Web 投递普通任务，不在任务文本里诱导注意力机制。
3. 采集日志和 WebSocket 事件。
4. 检查每次模型返回 usage 后，Web 面板或 `ATTENTION_UPDATE` 能看到最新：
   - `provider_prompt_tokens`
   - `provider_context_pressure_percent`
   - `provider_usage_source`
   - `pressure_tier`
5. 检查 green 状态没有把压力提示注入 LLM。
6. 检查 yellow / red 时才出现 LLM 压力提示和注意力选择引导。

## 非目标

- 不恢复每轮全量上下文注入。
- 不把绿色压力实时塞给 LLM。
- 不把 `backing_pool`、`backing_context_pressure` 等旧概念带回公开事件或 DOM。
- 不用前端显示需求替代动态注意力阈值触发逻辑。
