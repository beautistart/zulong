### 3.2 为什么会死循环？

**位置**：`ide_fc_runner.py:1880-1961 (_check方法)`

**问题1：弹性续期条件宽松**

```python
# 当前逻辑：只要达到hard_limit就续期
if fc >= self._hard_limit:
    # 无进展检测 → 检测失效
    if not self._is_progress_stalled(state):  # 总是返回False
        # 续期
        state.auto_continue_count += 1
        self._hard_limit += self._progress_report_interval
```

**问题2：_is_progress_stalled检测失效**

```python
def _is_progress_stalled(self, state: IDEFCState) -> bool:
    """安全阀：连续N次报告无进展"""
    if len(state.progress_reports) < self._max_reports_before_force_stop:
        return False
    
    # 检查最近的报告是否都无进展
    recent = state.progress_reports[-self._max_reports_before_force_stop:]
    
    # ⚠️ 关键：只检查completed_count是否增加
    # 但search_files不产生task节点，completed_count永远为0
    # 因此检测结果永远是"有进展"（因为0 → 0视为无停滞）
    first_completed = recent[0].get("completed_count", 0)
    return all(r.get("completed_count", 0) == first_completed for r in recent)
```

**问题3：无重复工具调用检测**

当前`_check()`方法**没有任何机制检测连续N轮调用相同工具**。

### 4.2 为什么发送失败？

**位置**：`ide_server.py:620-628`

```python

        "type": _msg_type,
```

**ASGI错误原因**：
- FastAPI/Uvicorn的WebSocket实现要求：发送消息必须在连接打开状态
- 用户关闭浏览器 → WebSocket发送close帧 → 连接状态变为"closing"
- 后端尝试发送消息 → ASGI拒绝（连接已关闭）

## 五、第三层根因：前端partial状态残留（核心问题）

### 5.1 前端思考状态判断逻辑

**位置**：`旧 IDE 内嵌前端（已移除）/src/components/chat/chat-view/components/layout/MessagesArea.tsx:148`

```typescript
// 判断是否显示"思考中"状态
const shouldShowThinking = 
    lastRawMessage.partial === true && 
    lastRawMessage.say === "api_req_started"
```

**partial状态来源**：
- Extension在发起API请求时发送`api_req_started`消息
- Extension在收到响应后发送`api_req_finished`消息
- `partial=true`表示请求进行中，`partial=false`表示请求完成

### 5.2 WebSocket断开后的状态流转

**Extension端**：`zulong-ide/src/core/api/providers/zulong.ts:208-212`

```typescript
this.transport.on("disconnected", (code: number, reason: string) => {
    Logger.warn(`[ZulongHandler] ← disconnected: code=${code} reason=${reason}`)
    // ⚠️ 只push done，不重置partial
    pushChunk({ type: "done" })
})
```

**问题**：
1. Extension收到`disconnected`事件后，只调用`pushChunk({ type: "done" })`
2. 这会终止generator循环，但**不会发送`api_req_finished`消息**
3. 旧 IDE 内嵌前端（已移除）的消息列表中，最后的`api_req_started`消息`partial`仍为`true`
4. UI持续显示"思考中..."

### 5.3 完整状态流转图

```

    ↓

    ↓

    ↓
```

### P0：后端消息缓存与重试

**目标**：WebSocket断开后，缓存task_complete消息供重连后拉取

**位置**：`ide_server.py`

```python
class PendingMessageCache:
    """待发送消息缓存（断线后重连恢复）"""
    _cache: Dict[str, List[Dict]] = {}  # session_id → messages
    _ttl = 300  # 5分钟过期
    
    @classmethod
    def cache(cls, session_id: str, msg: Dict):
        if session_id not in cls._cache:
            cls._cache[session_id] = []
        cls._cache[session_id].append({
            "msg": msg,
            "timestamp": time.time(),
        })
    
    @classmethod
    def pop(cls, session_id: str) -> List[Dict]:
        msgs = cls._cache.get(session_id, [])
        # 过滤过期消息
        now = time.time()
        valid = [m["msg"] for m in msgs if now - m["timestamp"] < cls._ttl]
        cls._cache[session_id] = []
        return valid

# 修改发送逻辑
try:
    await session.ws.send_json(msg)
except Exception as e:
    logger.warning(f"WS发送失败，缓存消息: {e}")
    PendingMessageCache.cache(session.session_id, msg)

# 重连时恢复
async def on_reconnect(session_id: str, ws):
    pending = PendingMessageCache.pop(session_id)
    for msg in pending:
        await ws.send_json(msg)
```

### P1：弹性续期条件收紧

**目标**：只有真正有进展才续期

**位置**：`ide_fc_runner.py:1918`

```python
def _is_progress_stalled(self, state: IDEFCState) -> bool:
    """增强版停滞检测"""
    if len(state.progress_reports) < 3:
        return False
    
    recent = state.progress_reports[-3:]
    
    # 检查1：completed_count是否增加
    completed_counts = [r.get("completed_count", 0) for r in recent]
    if completed_counts[-1] > completed_counts[0]:
        return False  # 有进展
    
    # 检查2：in_progress_count是否变化
    wip_counts = [r.get("in_progress_count", 0) for r in recent]
    if len(set(wip_counts)) > 1:
        return False  # 有变化
    
    # 检查3：消息长度是否增加（有新信息）
    if len(state.messages) > state.last_report_msg_count:
        state.last_report_msg_count = len(state.messages)
        return False  # 有新消息
    
    # 所有指标都无变化 → 停滞
    return True
```

```typescript
const THINKING_TIMEOUT = 5 * 60 * 1000  // 5分钟
let thinkingTimer: NodeJS.Timeout | null = null

useEffect(() => {
    // 监听思考状态
    if (isThinking) {
        // 设置超时
        thinkingTimer = setTimeout(() => {
            console.warn("思考状态超时，强制重置")
            dispatch({ type: "RESET_THINKING_STATE" })
        }, THINKING_TIMEOUT)

        // 清除超时

            clearTimeout(thinkingTimer)
            thinkingTimer = null
        }
    }
    
    return () => {
        if (thinkingTimer) clearTimeout(thinkingTimer)
    }
}, [isThinking])
```

## 十一、总结

1. 后端FC循环死循环 → 用户等待超时

**开发团队视角偏差**：

### 解决关键

**P0优先修复前端partial残留**：
- 这是用户直接感知的问题
- 修复成本低（30分钟）
