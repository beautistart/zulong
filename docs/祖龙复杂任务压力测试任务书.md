# 祖龙复杂任务压力测试任务书

> 目标：用真实、可验收、可打断恢复的复杂任务，压力测试祖龙是否能稳定完成长链路工程工作，并在出现问题时立即修复、重测，直到测试内容完整闭环。

## 1. 总体原则

本任务书拆成两个互相独立的压力测试任务：

1. **任务 A：Docker / SearXNG 独立配置压力测试**
2. **任务 B：真实大项目复杂编程压力测试**

两个任务必须分开执行、分开建 TaskGraph、分开写验收报告，不得把 SearXNG 配置混入复杂编程任务，也不得把复杂编程问题归因到 SearXNG 环境。

### 1.1 必须观察的祖龙能力

- 上下文压力监控与 CircuitBreaker 触发。
- 动态注意力调整：GLOBAL / SINGLE_CHAIN / FOCUS。
- TaskGraph 导航地图、节点地址感知与上下文覆盖率。
- CLI、cmd、PowerShell、Docker、浏览器自动化、Computer Use 能力检测。
- 外部目录任务稳定执行、打断、恢复。
- 复杂编程任务从分析、修改、测试到修复重测的闭环。
- ShardedMemoryGraph / Hybrid 超大体量图记忆存储压力。
- Web 端任务生命周期反馈是否符合 TSD：计划、动作、观察、进度、审批、总结清晰可见，内部控制提示不泄露。

### 1.2 问题即时修复硬规则

测试过程中出现任一问题，祖龙必须立即进入修复循环：

1. 定位问题原因。
2. 给出当前影响范围。
3. 执行最小必要修复。
4. 重跑刚才失败的命令、测试、页面验证或恢复步骤。
5. 将失败、修复、重测证据写入最终验收报告。

不得只记录问题后结束。只有以下情况允许输出 partial / blocked summary：

- 外部依赖确实不可用，且祖龙已经证明本轮无法修复，例如 Docker 服务未安装、系统权限拒绝、目标仓库缺失。
- 用户主动要求停止测试。
- 已达到明确的安全边界，继续操作会破坏非测试数据。

即使进入 partial / blocked summary，也必须列出已完成项、未完成项、失败证据、已尝试修复动作和下一步人工处理建议。

### 1.3 统一最终总结格式

每个任务结束时必须输出结构化总结，至少包含：

```json
{
  "completed_items": [],
  "verified_items": [],
  "pending_items": [],
  "risks_summary": [],
  "quality_score": 0.0,
  "quality_level": "pass|warn|iterate",
  "quality_iterations": 0,
  "task_graph_id": "",
  "workspace": "",
  "memory_changes": {}
}
```

不得只用自然语言说“已完成”。

## 5. 任务 B 附加段：超大体量图记忆存储压力测试

### 5.2 工作区

```text
D:\AI\zulong_stress_lab\memorygraph_scale_task
```

### 5.3 数据规模

必须生成或导入：

- 250,000-300,000 节点。
- 700,000-900,000 边。
- 至少包含 task / dialogue / knowledge / experience / episode / file 等多种节点类型。
- 至少包含 hierarchy / dependency / temporal / reference / semantic / association 等多种边类型。

### 5.4 运行态要求

必须压测：

- ShardedMemoryGraph / Hybrid 分片运行态。

- 跨分片边索引。
- active skeleton。
