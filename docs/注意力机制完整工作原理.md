# 注意力机制完整工作原理

> 本文对齐 TSD v2.9.21，并修正旧文档中过度强调“工具名触发”的表述。
> 当前规范：**L2 动态注意力的主触发信号是上下文压力阈值，主决策路径是 LLM 自主选择；普通工具事件只能进入工具账本、压力观测和质量证据，不得直接触发模式切换。**

---

## 一、核心定位

L2 动态注意力不是为了“压缩上下文”，而是为了让 LLM 在复杂任务和上下文压力上升时，**自己选择当前需要关注的上下文**：

- **按需注入**：把当前任务、焦点节点、依赖、未覆盖需求、工具证据、MemoryGraph 相关节点注入给 LLM。
- **暂排无关上下文**：把当前判断暂时不需要的分支降权或排除，减少干扰。
- **可恢复/可上浮**：当需要跨分支复核、补证据、完成质量审查或最终总结时，重新注入相关上下文或回到 GLOBAL。

因此，RED 阶段不应表述为“压缩上下文”，而应表述为：**触发动态注意力重选与按需注入**。

---

## 二、三种注意力模式

| 模式 | 作用 | 上下文行为 |
|---|---|---|
| GLOBAL | 全局规划、跨分支复核、最终总结 | 注入完整任务结构、跨分支依赖、覆盖缺口、风险与关键证据 |
| FOCUS | 局部节点、需求缺口、关键证据处理 | 注入焦点节点、祖先、依赖、相关工具结果和 MemoryGraph 证据，暂排无关上下文 |
| SINGLE_CHAIN | 单链执行、调试、连续推理 | 注入当前推理链必要上下文，保留可恢复的外部分支索引 |

---

## 三、主触发流程：上下文压力阈值

上下文压力监控的主要作用，就是触发 L2 动态注意力切换。

```text
上下文压力阈值监控
    ↓
压力达到配置阈值
    ↓
AttentionWindowManager 请求 LLM 自主选择 GLOBAL / FOCUS / SINGLE_CHAIN
    ↓
LLM 结合当前任务、TaskGraph、TaskSpec 覆盖缺口、MemoryGraph 证据、工具结果给出 mode + reason
    ↓
AttentionWindow 按选择结果注入必要上下文、暂排无关上下文，并记录可恢复索引
```

---

## 四、LLM 自主选择应输出什么

压力触发后，LLM 的注意力选择应包含：

1. **mode**：选择 GLOBAL / FOCUS / SINGLE_CHAIN。
2. **reason**：为什么当前需要全局、局部或单链上下文。
3. **focus_context**：当前关注的节点、需求缺口、证据或推理链。
4. **injected_context**：本轮需要注入哪些上下文。
5. **deferred_context**：哪些上下文被暂排，以及何时需要恢复。

---

## 五、工具事件的边界

固定工具名不得作为 L2 动态注意力切换的主规则绑定。

旧实现中类似：

- `_FOCUS_TRIGGERS`
- `_SINGLE_CHAIN_TRIGGERS`
- `_GLOBAL_FORCE_TRIGGERS`

已废弃为主规则。它们不能再直接驱动模式切换；普通工具事件只能作为上下文压力、质量证据和工具账本输入，不能作为规范验收中的固定映射。

正确原则：

```text
工具事件 = 账本/压力/质量证据输入
上下文压力 = 主触发信号
LLM 自主选择 = 主决策路径
```

这样才能兼容：

- `ide_write_file`
- `write_to_file`
- `exec_write_file`
- 远程 IDE 工具
- 未来新增工具
- 非编程任务

## 六、典型任务流程示例

```text
时间  场景                         压力/证据状态                 注意力行为
────────────────────────────────────────────────────────────────────────────
0s    理解用户目标                 压力低，需要全局规划          GLOBAL
8s    子任务展开                   压力中等，当前节点明确        LLM 可选择 FOCUS
20s   单链实现/调试                压力升高，链路依赖明确        LLM 可选择 SINGLE_CHAIN
40s   发现跨模块失败或覆盖缺口      需要补充其他分支证据          重新注入相关上下文
60s   完成前质量复核               需要核对原始任务和全局风险    回到 GLOBAL
```

示例中的切换由上下文压力和 LLM 自主注意力决策驱动，不要求绑定到某个固定工具名。

## 七、与 CircuitBreaker RED 的关系

RED 不是简单地“停止工具并压缩上下文”。建议分层处理：

1. **RED-1：纠偏**
   如果任务未完成或 TaskSpec 未覆盖，优先注入未完成/未覆盖项，要求继续修正。

2. **RED-2：动态注意力重选**
   触发 LLM 基于压力、当前节点、覆盖缺口和证据状态重新选择注意力模式，并按需注入必要上下文。

3. **RED-3：便签锚定 + 受限注意力重选**
   第三次 RED 不直接强制中断，也不把上下文简单压缩成摘要；应先把当下可用证据、未完成项、失败原因、当前焦点节点写入“便签”，并挂到当前 TaskGraph / MemoryGraph 焦点节点。随后进入一次受限工具回路：收走普通执行工具，只保留“便签/记忆落盘能力”和“注意力切换能力”，强制 LLM 选择 GLOBAL / FOCUS / SINGLE_CHAIN 之一重新组织上下文。

4. **覆盖感知收束**
   受限恢复回路之后，如果 TaskSpec 覆盖通过，允许最终总结；如果覆盖不通过，只能输出 partial/blocked summary，不能伪完成。

受限工具回路的保留集合应按**工具能力类别**定义，而不是按具体工具名硬编码：

- 便签/记忆落盘能力：例如 `save_memory_note`，或等价的 TaskGraph note 节点创建能力。
- 注意力切换能力：例如 `navigate_attention` / `adjust_attention_mode`，或未来等价的动态注意力接口。

当前代码中 `save_memory_note` 已会把笔记引用到 MemoryGraph 当前焦点任务节点；若运行态无法取得 MemoryGraph 焦点，应退化为在 TaskGraph 当前节点下创建 note 节点。

## 八、验收口径

动态注意力验收不应再使用“调用某固定工具名必然切换到某模式”作为主标准。

应观察：

- 上下文压力值和阈值是否被记录。
- 压力超过阈值时是否触发 LLM 自主注意力选择。
- LLM 是否给出 mode / reason / focus_context。
- FOCUS / SINGLE_CHAIN 是否按需注入当前必要上下文。
- 暂排上下文是否可恢复。
- 任务完成、质量复核或跨分支判断时是否能重新注入上下文或回到 GLOBAL。
